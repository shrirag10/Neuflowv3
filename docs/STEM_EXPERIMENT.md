# Full-resolution stem — experiment record

Run 2026-08-08/09. **Deliberately excluded from the defence presentation**: the
effect is real in direction but below what a single seed resolves, and a result
that cannot be claimed does not belong on a slide. Kept here in full so it can be
picked up for a paper revision, a future-work section, or a follow-up run.

---

## The hypothesis

Every input to the implicit decoder sits at 1/8 or 1/16 resolution:

| input | resolution |
|---|---|
| context | 1/8 |
| features | 1/8 |
| features | 1/16 |
| warped frame-1 features | 1/8 |
| coarse flow | 1/8 |

Two queries inside the same 8x8 cell therefore sample nearly identical evidence,
because bilinear interpolation of a 1/8 map over a sub-pixel distance is close to
a linear ramp. The decoder cannot distinguish them, so a "sub-pixel query" is a
smooth interpolation of the coarse field rather than an inference from finer
evidence.

That single mechanism was proposed to explain three separate null results:

1. **Fourier positional encoding** of the sub-cell offset: null, 2.288 against
   2.275, slightly worse. It told the decoder *where* in the cell it sat while
   nothing varied with that position.
2. **Sub-pixel querying**: behaved as interpolation.
3. **Reduced-resolution coarse flow with full-resolution queries**: matched
   bilinear upsampling exactly.

**What v2 does instead.** Its upsampler runs `conv_s8`, an 8x8 kernel at stride 8
over the *full-resolution* image, so each cell's 128-channel vector has encoded
that entire patch of raw pixels. `UpSample` then emits `8*8*9 = 576` channels,
reshaped to `[B, 1, 9, 8, 8, H, W]` and softmaxed over the 9: **a separate set of
nine convex weights for every sub-position in the cell**, each conditioned on
full-resolution content. v3 dropped that and replaced it with a decoder holding no
full-resolution evidence at all.

**Prediction.** Give the decoder a full-resolution stem and (a) sub-pixel accuracy
improves, (b) the PE stops being null, because it finally has content to index
into. (b) is the sharper prediction: it is an interaction effect, so it is harder
to get right by accident.

## What was built

`NeuFlow/implicit_decoder.py`, behind `use_stem`:

```python
self.stem = nn.Conv2d(3, stem_dim, kernel_size=8, stride=8, padding=0, bias=False)
self.win_proj_stem = nn.Linear(k2 * stem_dim, stem_dim)
```

Sampled through the same local-window projector as the other four sources and
concatenated into the MLP input, which grows from 260 to 388. Mirrors v2's
`conv_s8` deliberately rather than inventing a new mechanism.

- 205k new parameters, 8.03 M total, still below v2's 9.03 M
- Lives inside `implicit_decoder_module`, so the existing freeze makes it
  trainable while the front end stays frozen: 950,154 trainable, 15 BatchNorm
  layers held in eval
- Zero-init still reproduces bilinear upsampling to 0.0079 px, **identical to the
  non-stem model**, so the known-good starting point is preserved
- Stem and non-stem checkpoints are not interchangeable; `--stem` must match
  between train and eval, and mismatches fail loudly

Flags: `train.py --stem`, `scripts/eval_vkitti2.py --stem`. Jobs generated by
`hpc/make_sbatch.py`.

## How it ran

Two jobs, `nf3-stem` and `nf3-stem-pe`, identical to
`v3_FlyingChairs_VKITTI2_Sintel` in every other respect: seed 1234, batch 16,
2e-4 OneCycle, gamma 0.8, 4,096 queries, 1x s16 + 8x s8.

**Both hit the 8 h wall at ~84k of 100k steps** and last saved at step 80,000.
The stem averages **2.94 step/s against the baseline's 4.64**, so 100k needs about
9.5 h. The extra cost is the fifth window sample plus a 1152→128 projection per
query, at 4,096 queries per batch element.

Rather than compare an 80k stem against a 100k baseline, which moves two
variables, all three were evaluated at step 80k. The baseline keeps every 5k
checkpoint, so this needed no extra training.

**The truncation costs nothing measurable.** Baseline at 80k scores 2.3933 /
75.78% against its own 100k 2.392 / 75.83% — 0.001 px and 0.05 points apart, far
below the resolution limit. 80k is effectively converged, so the matched
comparison is sound rather than a compromise.

## Results

VKITTI 2 Scene18+20, 1,174 pairs, 460,573,660 valid pixels, fast_dense stride 2,
all at step 80,000.

| run | EPE | 1px | 3px |
|---|---|---|---|
| baseline, no stem | 2.3933 | 75.78% | 88.98% |
| + stem | 2.3885 | 75.90% | 88.97% |
| **+ stem + PE** | **2.3713** | **76.07%** | **89.14%** |
| *NeuFlow v2* | *2.324* | *77.63%* | *89.80%* |

Gap closure for stem+PE against v2: **32% of the EPE gap** (0.022 of 0.069),
**16% of the 1px gap** (0.29 of 1.85 points).

---

## Interpretation

**Direction confirmed, magnitude not claimable.**

Everything moved as predicted, and the interaction effect appeared: the PE was
*worse* than nothing on its own (2.288 against 2.275) and now contributes more
than the stem does alone, −0.017 on top of the stem's −0.005. That is the sharp
prediction from the mechanism and it held.

But 0.022 px sits below the ~0.05 px that a single seed resolves, and the
0.29-point 1px gain is the same size as the uncertainty head's gain, which this
project already declines to claim for exactly that reason. **The stem does not
close the accuracy gap**, and no honest reading of one seed says otherwise.

The mechanism is therefore better described as *supported but not sufficient*: the
1/8-resolution bottleneck is real and relieving it helps, but a stride-8 summary
of the patch recovers only a fraction of what v2 gets from reading full resolution
directly.

---

## What would resolve it

In rough order of value:

1. **Multiple seeds.** An effect this size needs 3 to 5 seeds per configuration to
   separate from checkpoint noise. Nothing else on this list matters until the
   effect is resolved.
2. **A richer stem.** Stride-8 compresses an 8x8 patch into one vector. Sampling a
   1/2 or 1/4 resolution feature map directly at the query coordinate would let
   the evidence genuinely vary within the cell rather than being summarised.
   Costs memory and decode time.
3. **Match v2's output structure.** v2 predicts 64 weight sets per cell, one per
   sub-position. The decoder predicts one set per query. Closing that gap is a
   larger change than the stem.
4. **A properly annealed run.** Set `STEPS = 80000` in `hpc/make_sbatch.py` so
   OneCycle completes inside the wall. Low value: baseline 80k and 100k differ by
   0.001 px, so annealing is not what limits this.
